# v3-dev 记忆召回与回复质量规划

基线为上游 09439a5。人物插件已经保存带证据和版本的主张，并在召回时检查场景及账号归属。第一阶段复用现有经历表和评分入口。

## 第一阶段 · 混写关键词（本分支）

保留完整查询词，补充汉字和相邻非汉字片段，再生成汉字双字片段。显式查询词优先占用 24 个词的预算。混写拆分忽略单字符片段，用户单独输入的单字仍有效。数据库筛选与内存评分沿用同一组词。新增回归用例覆盖分隔写法、原词排序与预算。

## 第二阶段 · 离线回放

用固定的合成历史对比上游 `09439a5` 和混写分支 `f644aab`。查询为「上次 Koishi配置」，目标来源是群聊中的「Koishi配置」和私聊中的「Koishi 的配置」。另有一个已撤回权限的群、一条账号改绑前的旧经历，以及仅提到 Koishi 启动的无关消息。

| 样例 | 上游前六条 | 初版混写前六条 | 分配候选名额后 |
| --- | --- | --- | --- |
| 基本场景 | 1 条相关 | 2 条相关、1 条无关 | 2 条相关、1 条无关 |
| 加入 200 条较新的单词命中 | 1 条相关 | 0 条相关、6 条无关 | 2 条相关、4 条无关 |

用三版实际 `ContinuityStore.recall` 运行上述比较，数据库查询由内存替身执行，三个版本均返回 0 条撤权或归属已失效的来源。另加 Koishi 集成回归，经 `person_recall` 和自动注入检查来源 ID 和 4,000 字符预算。

200 条上限在数据库按时间截断候选时生效，正文评分在截断之后。扩大分词后，较新的单词命中可能先占满候选窗口，强命中随之丢失。现在完整混写词和完整片段匹配各预留至多一页候选，其余名额由普通关键词匹配补足。查询按来源 ID 去重，候选总数最多 200 条，最终仍按关键词得分和时间排序。混写查询最多增加两次数据库读取。真实群聊的样本分布、查询时间和不同数据库驱动的表现仍需测量。

## 第三阶段 · 后台维护

人物总结使用数据库保存任务输入、输出和回执。现有集成用例覆盖插件重载后复用保存结果、权限撤回后阻止写入，以及全量清理期间丢弃旧工作。通用工具注册表增加重载用例，验证旧任务迟到时不会向新实例结算，同一会话仍能正常提交新任务。

通用搜索、网页读取和图片描述的结果绑定到原对话轮次。保留进程内生命周期。需要跨重启的只读任务，应先具备稳定的任务标识、结果消费者、有效期和恢复时的权限检查，再评估是否复用持久队列。

## 第四阶段 · 回复预设对照

[离线对照](reply-preset-evaluation.md)提供候选预设、六个共同样例及盲评记录，涵盖短对话、引用、长解释、工具超时和静默。原生工具与 JSON fallback 分别运行，评价接话、角色语气、事实和实际动作。根据真实模型输出决定是否采用候选预设。
