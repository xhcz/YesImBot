# v3-dev 记忆召回与回复质量规划

基线为上游 09439a5。人物插件已经保存带证据和版本的主张，并在召回时检查场景及账号归属。第一阶段复用现有经历表和评分入口。

## 第一阶段 · 混写关键词（本分支）

保留完整查询词，补充汉字和相邻非汉字片段，再生成汉字双字片段。显式查询词优先占用 24 个词的预算。混写拆分忽略单字符片段，用户单独输入的单字仍有效。数据库筛选与内存评分沿用同一组词。新增回归用例覆盖分隔写法、原词排序与预算。

## 第二阶段 · 离线回放

用固定的合成历史对比上游 `09439a5` 和混写分支 `f644aab`。查询为「上次 Koishi配置」，目标来源是群聊中的「Koishi配置」和私聊中的「Koishi 的配置」。另有一个已撤回权限的群、一条账号改绑前的旧经历，以及仅提到 Koishi 启动的无关消息。

| 样例 | 上游前六条 | 混写分支前六条 |
| --- | --- | --- |
| 基本场景 | 1 条相关 | 2 条相关、1 条无关 |
| 加入 200 条较新的单词命中 | 1 条相关 | 0 条相关、6 条无关 |

用两版实际 `ContinuityStore.recall` 运行上述比较，数据库查询由内存替身执行，两版均返回 0 条撤权或归属已失效的来源。另加 Koishi 集成回归，经 `person_recall` 和自动注入检查来源 ID 和 4,000 字符预算。

200 条上限在数据库按时间截断候选时生效，正文评分在截断之后。扩大分词后，较新的单词命中可能先占满候选窗口，强命中随之丢失。下一轮先验证精确词组与拆分词分别取候选再合并的方案，比较目标命中、无关来源、权限过滤和查询时间。真实群聊的样本分布仍需测量。

## 第三阶段 · 后台维护

用人物总结的持久队列作对照，分别验证重启、取消、清理期间的迟到回写。对确有跨重启价值的只读任务再设计恢复策略。参考 Anthropic 的 The components of agent memory 和 Building always-on agents。

## 第四阶段 · 回复预设对照

选同一批短对话和长解释，盲评接话、角色语气及事实保真。参考 lieflat-less-ai-tone 的候选复核方法，对异常举出具体原句。用 Spec Kit 的规格与验收思路记录实验条件及结果。
